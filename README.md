# OPUS Benchmark Outlier Analysis

Compare outlier-detection methods for repeated OPUS GPS observations of NOAA
CO-OPS tidal benchmarks, produce an outlier-cleaned per-benchmark geodetic
elevation, and join those results to CO-OPS tidal datums.

The full write-up (rationale, methodology, results, and figures) is in
**[`docs/In_Depth_Report.md`](docs/In_Depth_Report.md)**.

## Background

Each tidal benchmark (identified by an NGS **PID**) may be occupied by GPS/OPUS
many times over the years. To relate a benchmark's geodetic height to the
station's tidal datums, we need a single representative elevation per mark that
is **not polluted by outlier observations**.

The long-standing CO-OPS practice applies a **4 cm tolerance among different
benchmarks** (a spatial, inter-mark check). This project instead evaluates
outlier detection applied to **repeated observations of the same mark over
time** (a temporal, intra-mark problem) and compares several methods to
recommend a defensible workflow for the NAPGD2022-era datum ties.

> **Important framing:** real observations have no ground-truth "outlier" label,
> so no method can be graded on "did it find the true outlier." Instead we judge
> methods on **robustness** (resistance to being fooled by the bad point itself),
> **stability** (how little the resulting average moves), and behavior under a
> controlled **synthetic-outlier injection experiment**.

## Outlier methods compared

| Method | Rule | Character |
|--------|------|-----------|
| `fixed` | \|x − mean\| > 4 cm | absolute / physical |
| `s1` (1σ) | \|x − mean\| > 1·std (~68%) | relative, non-robust |
| `s2` (2σ) | \|x − mean\| > 2·std (~95%) | relative, non-robust |
| `mad` | modified z = \|x − median\| / (1.4826·MAD) > 3.5 | **robust** |
| `consensus` | flagged by ≥ 2 of the four methods | combined |

Each method's **cleaned average = mean of the surviving (non-flagged)
observations**. Group-size policy: `n=1` keep the single value; `n=2` plain
mean; `n≥3` run the full comparison. All marks (including `n<3`) still join to
CO-OPS — only the outlier *detection* is skipped for small groups.

## Requirements

- Python 3.11+
- **Analysis stages (s01–s06):** standard library + `openpyxl` only.
- **Figures (s07):** `matplotlib`, `numpy`.
- **GeoPackage export (s08 step 2):** `geopandas` (+ `shapely`, `pyproj`, `fiona`).

Create the environment (conda-forge recommended, especially on Windows):

```bash
conda create -n bm_outlier -c conda-forge python=3.12 matplotlib numpy openpyxl geopandas
conda activate bm_outlier
```

## Input data

The analysis reads two source workbooks from a local **`data/`** directory (path
configurable in `config.py`). **These files are not committed to the repo** — they
are compiled extracts of publicly-available data and should be pulled fresh from
the authoritative sources:

- `data/OPUS__3-10-26.xlsx` — OPUS observations (many rows per PID), derived from
  the **NGS OPUS** published datasheets / GIS feature layer.
- `data/CO-OPS__3-12-26.xlsx` — CO-OPS tidal datums (one row per PID-per-station),
  from the **CO-OPS** benchmark/datums holdings (public datums pages / API).

Place both files in `data/` before running. Paths, temporal windows, and all
method parameters live in **`config.py`** — the single place to review or change
how the analysis behaves.

## How to run

```bash
conda activate bm_outlier
python run_all.py            # full pipeline (analysis + figures + GeoPackage)
```

Selective runs:

```bash
python run_all.py --core        # analysis stages only (no figures/GIS)
python run_all.py --from s04     # resume from a stage
python run_all.py --only s06     # run a single stage
```

> **Windows note:** run via `conda activate bm_outlier` first, then `python`.
> Invoking the environment's `python.exe` by full path can cause matplotlib DLL
> load failures. This does not affect Linux.

## Pipeline stages

| Stage | Script | Produces |
|-------|--------|----------|
| s01 | `load_normalize` | clean OPUS table (PID normalized, dates parsed) |
| s02 | `window_filter` | tags each obs with temporal-window membership |
| s03 | `group_methods` | per-observation four-method flags (audit trail) |
| s04 | `per_pid_summary` | per-PID stats + each method's cleaned average |
| s05 | `injection_experiment` | synthetic-outlier detection / false-alarm rates |
| s06 | `deliverables` | CO-OPS joins (A, B, C) + station spatial screen (D) + PID coverage report |
| s07 | `figures` | eight presentation figures (PNG) |
| s08 | `gis_export` | per-PID points CSV + GeoPackage layer |

## Temporal windows

Observations are analyzed within three (nested) windows, set in `config.py`:

- `W_NTDE` — 2002-01-01 to 2020-12-31 (current National Tidal Datum Epoch)
- `W_MOD` — 2002-01-01 to present
- `W_ALL` — all observations

## Outputs (`outputs/`, regenerated by `run_all.py`)

- `tables/`
  - `s06_deliverableA_join_mostrecent.csv` — CO-OPS × most-recent OPUS obs per (PID, window)
  - `s06_deliverableB_join_avg.csv` — CO-OPS × cleaned/representative height per (PID, window)
  - `s06_deliverableC_method_compare.csv` — per-mark method comparison (raw vs each cleaned average + induced shift)
  - `s06_deliverableD_station_spatial.csv` — per-station inter-mark screen (temporally-cleaned mark elevations; 4 cm spatial gate vs robust screen)
  - `s06_join_coverage.csv` — PID overlap (in both / OPUS-only / CO-OPS-only)
  - plus intermediate stage CSVs and the injection-experiment results
- `figures/` — `fig1`…`fig8` PNGs (fig7/fig8 = station-level temporal vs spatial examples)
- `gis/`
  - `s08_pid_points.csv` — per-PID points (usable in ArcGIS Pro via *Add XY Data*, X=`lon_dd`, Y=`lat_dd`, NAD83)
  - `opus_outlier_results.gpkg` — GeoPackage point layer `pid_outlier_results` (EPSG:4269), including a `method_spread_m` attribute that quantifies how much the methods disagree at each mark

## Notes on GIS / ArcGIS Online

The pipeline is intentionally **Esri-agnostic**: it writes an open GeoPackage
so results can be examined without any Esri license. Publishing to ArcGIS
Online is handled separately (via the ArcGIS API for Python using an existing
ArcGIS Pro sign-in) and is not part of the automated pipeline.
